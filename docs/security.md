# Security: fifty common holes in web apps, checked

*Each item on the list, checked against UniverList: the site, its Worker (`/api`, with Account & sync under
`/api/sync`), the one-file build and extensions. ✅ dealt with, and how it's kept that way · ➖ doesn't apply, and why ·
⚠️ a trade-off, said plainly.*

| # | Hole | | Here |
|---|---|---|---|
| 1 | Exposed database credentials | ✅ | There are none to expose: the Worker reaches D1 and R2 through bindings, not passwords. The database id in `wrangler.jsonc` is only a name; nothing can be done with it without your Cloudflare login |
| 2 | Public .env files | ✅ | Local secrets live in `.dev.vars`, which is git-ignored and never in `dist/` (only `public/` and the build go there) |
| 3 | Hardcoded API keys | ✅ | None in the code. Server keys are Worker secrets; people's own keys stay in their own browser. The keys the site lends (TMDB, IGDB) are added inside the Worker and never sent back: tested |
| 4 | Weak or missing authentication | ✅ | Passkeys (WebAuthn) with user verification, checked on the server by `@simplewebauthn/server`; no passwords exist to guess. `account.cjs` signs up and in with real (virtual) passkeys. **Confirm it's you:** deleting the account, a new recovery code, adding or removing a passkey, and letting a passkey unlock your library all need the passkey or the recovery code within the last 5 minutes (signing in with either counts), so a device that got in another way (a QR code someone else scanned) can't lock you out or keep itself a way back in. What such a device *can* do is save over your library; the cloud then still has your last three versions and the newest one more than a day old. `sync.test.js` and `account-link.cjs` check it. |
| 5 | No authorization checks | ✅ | Every Account & sync route after sign-in needs a valid session; `sync.test.js` checks each one refuses without |
| 6 | Users able to access other users' data | ✅ | No route takes an account id: every query uses the session's own. `sync.test.js` has a second account try to read, change and revoke the first's |
| 7 | Open database read/write permissions | ✅ | D1 and R2 can only be reached through the Worker's bindings; nothing is public |
| 8 | Misconfigured Firebase / Supabase / S3 buckets | ✅ | The R2 bucket has no public access (don't switch on its r2.dev address: nothing needs it) |
| 9 | Admin routes left unprotected | ➖ | There are no admin routes. `/api/status` only says which sources are set up, never a key |
| 10 | Debug pages exposed in production | ✅ | None in the build. Test pages and fixtures never go into `dist/` |
| 11 | Build logs leaking secrets | ✅ | CI passes the Cloudflare token as a secret (masked in logs); nothing prints keys |
| 12 | Verbose errors leaking stack traces | ✅ | The Worker answers "something went wrong" and nothing more; tested |
| 13 | Leaked GitHub repos or commit history | ✅ | CI runs Gitleaks (a fixed release, checked against its fingerprint) over every commit on every push, and the identity guard (`tools/guard.mjs`) fails on any private word in any file, any earlier version of a file, the files inside a zip, a picture's metadata, or a commit's author, committer or message. Both run on every push to main and ran clean before the first commit. Exports and backups are git-ignored |
| 14 | Secrets in frontend JavaScript | ✅ | The built files were scanned for key and token patterns: none |
| 15 | Client-side-only security checks | ✅ | Every rule for accounts (who you are, which data, sizes, versions, limits) is enforced on the server; the app's checks are only for nicer messages |
| 16 | Missing input validation | ✅ | The Worker checks every body: sizes (64 KB JSON, 20 MB data, 2 KB key), types, versions, names; the proxy allows plain path names only. In the app, a shared backdrop file (Backdrop builder) goes through one check, `cleanWorld()`: only known fields, every number clamped, a picture only as an inline JPEG/PNG/WebP (never a link, which would tell another site when you open the app, and never SVG, which can carry script); `worlds.test.js` tries the bad ones |
| 17 | SQL injection | ✅ | Every query is prepared with bound values; the only names put into SQL are a fixed list in the code |
| 18 | NoSQL injection | ➖ | No NoSQL store. Imported JSON is data only, with `__proto__` keys dropped |
| 19 | Cross-site scripting (XSS) | ✅ | Everything shown is escaped; links from data only ever open `http(s)`; and the site's policy runs no inline script. `xss.cjs` fills every field with attacks and visits every page; `csp.cjs` checks an injected script doesn't run |
| 20 | Cross-site request forgery (CSRF) | ✅ | SameSite=Strict cookies, plus every change needs the app's own header and this site's Origin; tested both ways |
| 21 | Insecure file uploads | ✅ | Imports are read in your own browser, as data. A zip is unpacked with hard limits checked while it unpacks (60,000 files, 512 MB a file, 2 GB in all), so a "zip bomb" stops early instead of filling memory; a picture's kind is read from its first bytes, never trusted from its name, and only PNG, JPEG, GIF, WebP and AVIF are kept (never SVG, which can carry script), 8 MB each at most; `import-limits.cjs` tries them. The only upload is the sync blob: size-capped, stored as opaque bytes, never run or served to anyone else |
| 22 | Path traversal | ✅ | R2 keys are built from the server's own ids; proxy paths allow plain names only (encoded slashes, dot-names and odd bytes refused); tested |
| 23 | Server-side request forgery (SSRF) | ✅ | The proxy only calls fixed API hosts; `/page` reaches university and reading-list sites only, following redirects itself and checking every hop (five at most), reads at most 6 MB, and hands the page back as plain text inside a sandbox, so nothing fetched can run or show as a page of this site; ScreenScraper pictures only through links the proxy signed itself, and only pictures come back; tested |
| 24 | Broken password reset flows | ➖ | No passwords, so nothing to reset. Up to ten passkeys and one recovery code per account. Another device signs in with a QR code from one that's signed in (one use, ten minutes, the key's secret only after the `#`; no passkey made). Lost passkey: the recovery code signs in (the server keeps only the hash of a key derived from it, separately from the one that unlocks) and a new passkey replaces the old one. Lose both and every device, and the cloud copy can't be opened, by design |
| 25 | Weak session management | ✅ | 256-bit random tokens; only their hash is stored; 30 days; you can see and sign out every device; signing out deletes the session |
| 26 | JWT secrets weak, leaked or reused | ➖ | No JWTs: sessions are random tokens checked against the database |
| 27 | Overly permissive CORS | ✅ | Account & sync offers no CORS at all (same site only). The catalogue proxy is open (`*`) on purpose: it holds no user data and sends no cookies |
| 28 | Rate limits missing (login, signup, APIs, AI) | ✅ | Sign-in and sign-up: 10 a minute per address; `/api`: 60 (an IPv6 address counts by its whole /64 block, so one connection can't pose as millions). Lookups on the site's own TMDB and IGDB keys refuse other websites, make only the lookups the app makes, come from a shared one-day cache, and are capped at 30 new ones a minute per address and 180 a minute in total, so even a script pretending to be the site can't run the keys past their limits. Your other keys answer only with the proxy password, which travels in a header, never an address; Hardcover's can only read. Cost limits that keep R2 (the only part that can bill) inside its free tier even if every account is abused: 100 accounts unless `MAX_USERS` says otherwise, and per account 300 saves and 1,000 reads a day (`DAILY` in `worker/sync.js`, tested). Accounts that never turned sync on are cleared after a day, and accounts that never saved a library after a week, so bots can't hold the places; each account's activity list keeps its latest 200 entries. There are no AI calls. Signed-in steps that write (QR codes, passkey and confirm requests) count toward each account's daily allowance. ⚠️ Someone determined, with a hundred passkeys, could still sign up and save once in each account and hold every place: new sign-ups then get "no new accounts right now" until you raise `MAX_USERS` or delete those rows. Nothing breaks and nothing bills, and the people already in keep working. |
| 29 | Public test or staging environments | ✅ | None. The browser tests run the site on the test machine only (`wrangler dev --local`, throwaway data) |
| 30 | Default credentials left unchanged | ✅ | None exist. Companions only listen on 127.0.0.1, and refuse to start when shared (PUBLIC_URL set) without passwords you choose |
| 31 | Webhooks without signature verification | ➖ | No webhooks |
| 32 | Payment checks only on the frontend | ➖ | No payments. The support link goes to GitHub Sponsors, which handles payment itself |
| 33 | Insecure direct object references (IDOR) | ✅ | Same as 6: nothing reachable by naming an id. Older versions are looked up under your own account only |
| 34 | API endpoints trusting user-controlled IDs or roles | ✅ | No roles; ids from requests are ignored for whose data it is |
| 35 | Logs with tokens, emails, passwords, private data | ✅ | Nothing personal is logged. The audit list keeps "Chrome on Mac", never addresses. No emails are collected at all |
| 36 | Source maps exposed in production | ✅ | None built (checked) |
| 37 | Dependency vulnerabilities | ✅ | `pnpm audit --prod`: none (SimpleWebAuthn moved to 14 for this). CI stops on any serious one. A few low/moderate remain in build-only tools that never reach the site |
| 38 | Outdated packages | ✅ | Dependabot opens a pull request weekly for packages and Actions; CI tests each |
| 39 | Prompt injection in AI features | ➖ | No AI features. (An AI assistant extension was removed before 1.0; a copy added earlier is deleted from the device, saved key and all, and an old backup's copy isn't brought back) |
| 40 | AI tools/actions reaching data without checks | ➖ | No AI tools or actions |
| 41 | Excessive database permissions for the app user | ✅ | The Worker's bindings reach one database and one bucket, nothing else in your account |
| 42 | No audit logs | ✅ | Every account has its own list: created, signed in, passkeys added and removed, devices signed out, passphrase changed |
| 43 | No monitoring or alerting | ⚠️ | Worker observability is on (errors and request counts in the Cloudflare dashboard). Alerts are one setting away: Cloudflare › Notifications › "Workers" (e-mail when errors spike); it can't be switched on from the code |
| 44 | No backup or restore plan | ✅ | Your library: "Download everything" any time, and the cloud keeps your last three versions, plus the newest one from more than a day ago ("Go back to this"). The accounts database: D1 Time Travel restores any minute of the last 30 days (`wrangler d1 time-travel restore`) |
| 45 | Publicly exposed internal dashboards | ➖ | None. Cloudflare's dashboard is behind your Cloudflare login (turn on two-factor there) |
| 46 | Missing security headers | ✅ | Content-Security-Policy, HSTS, X-Frame-Options, nosniff, Referrer-Policy, COOP, CORP, Permissions-Policy on the site and the Worker; tested under the real headers |
| 47 | Cookies missing HttpOnly, Secure or SameSite | ✅ | The one cookie is `__Host-`, HttpOnly, Secure, SameSite=Strict, Path=/; tested in the browser |
| 48 | Unencrypted sensitive data | ✅ | The synced library is encrypted end to end (AES-256-GCM). Its key is stored only sealed: per passkey, by a key made with HKDF-SHA256 from the passkey's own PRF secret, which is taken out of the passkey's answer before anything is sent (`account-passkey-unlock.cjs` checks no request carries it); and by your recovery code (PBKDF2-SHA256, 600,000 rounds); for ten minutes while you add a device, by a secret that exists only in the QR code (after the `#`, never sent: `account-link.cjs` checks). Every box names the key it seals (a fingerprint), and the server holds each account to one key: turning sync on is one all-or-nothing request, so two devices doing it at once can't leave two keys; each upload has its own file, so two saving at once can't overwrite each other (both tested). The private collection is sealed on the device too, with its own passphrase, and so are backups' private parts. ⚠️ A list made inside the private collection keeps its name and notes unsealed, on the device and in a backup that includes the collection (the things in it are sealed); in the cloud it's still encrypted end to end like everything else. ⚠️ On each signed-in device the key is kept in that browser (so it can sync by itself and add devices), readable only by the site's own scripts, like the library itself; API keys you type are kept the same way. In backups, an extension's secret settings (a companion password) are never written in the clear: they're sealed with your keys by the backup passphrase, or left out (`ext-secrets.cjs`). |
| 49 | Poor tenant isolation | ✅ | Every row and blob belongs to one account and every query is scoped to the session's account; tested with two accounts |
| 50 | Shipping code nobody checked | ✅ | Nothing ships unchecked: Biome and Knip, type checks, unit tests (the Worker's sync on a real SQLite, the proxy, the store, every button's handler), and over 40 browser test files including this list's attacks and an accessibility sweep. Security-critical parts use reviewed libraries (SimpleWebAuthn, the browser's WebCrypto), not home-made crypto |
