# Decisions

*Every tool UniverList is built with, what it was weighed against, and why it won. A dependency has to remove more than
it adds: when one is added or swapped, its line here changes in the same commit.*

---

## The app

| Part | Chosen | Why, for this app | Weighed against |
| --- | --- | --- | --- |
| Licence | **GNU AGPL-3.0 only**, with a permission for extensions and a credit line (section 7 terms in `ADDITIONAL-TERMS.md`) | Anyone can use, change and host it, but a changed copy that others use has to share its changes, so nobody can close it into a paid product. Extensions can use any licence. Moving to a more permissive licence later stays possible while the code is mine; going the other way couldn't be undone for versions already out | MIT (allows closed, paid copies), Apache-2.0 (the same, plus patents), GPL-3.0 (doesn't reach copies run as a website), MPL-2.0 (made for libraries) |
| Language | **TypeScript**, strict, for the whole app (`src/`: every module, with Svelte for the components) and the Worker. No `any`; what comes from outside (files, servers, storage, messages) arrives as `unknown` and is checked by the guards in `core/core.ts`. The tests, the tools (`tools/`) and the config files are TypeScript too, strict, checked by `pnpm check` (`tests/tsconfig.json`). The only JavaScript left is the official extensions (`extensions/`: they run in the extension sandbox as they are, and the local media player's companion runs on Node 18 or Deno) | A large, long-lived data model. Types catch wrong field names and shapes that drift between modules before anything runs | JavaScript with JSDoc types |
| Interface | **Svelte 5** | The hardest bugs came from redrawing whole parts of the page on every change: search losing the cursor, a dialog losing what you typed, focus jumping. Svelte updates only what changed, and compiles to small plain JavaScript | SolidJS: as fast, smaller ecosystem. React: more code for the same thing (memoising to stop re-renders) and a bigger runtime; its UI kits matter little for an app with its own design |
| No server framework | — | Next.js and similar are built around rendering on a server. UniverList has no server for your library and must run from one file on disk | — |
| Styling | **SCSS**, with **CSS custom properties** for everything a theme changes | Themes, including ones people make, change colours and fonts while the app runs, which only custom properties can do. SCSS adds nesting and partials at build time | Tailwind: fixed at build time, which fights user-made themes, and it buries the design in class lists |
| Motion | **CSS** transitions and keyframes (`transform` and `opacity` only), Svelte's `transition:` and `animate:flip`; one `<canvas>` for backdrops people build | Covers everything the app does, costs nothing to download, and respects reduced motion | Motion (motion.dev), if a sequence ever needs timelines or springs |
| Long lists | **My own row windowing** (`library/page/rows.ts`, `shelf.svelte.ts`, about 300 lines): past 300 entries the library page draws, in each group, the rows within a window's height of the screen, with an empty block as tall as the rest above and below. The rows are the page's own (a CSS grid's columns read from the shelf, wrapping spines and true-size covers broken where the browser breaks them, a table's rows, with the few rows that decide its columns' widths kept in out of sight, `columns.ts`), measured once drawn | 10,000 entries scroll smoothly and every one can be reached (the List view stopped at 2,000 rows a group, and the shelves added 96 tiles at a time and never let any go): in the stress test, about 3,600 page elements drawn instead of 8,000, and 5,500 instead of 17,700 after scrolling a long way. Each shelf keeps its own layout, so what's on screen is laid out as if every tile were drawn and the markup, styles and browser tests stay as they were. Trade-offs: the browser's find-in-page and a screen reader's list only reach rows near the screen (a table says its full length, `aria-rowcount`); "one row per shelf" draws every tile | **TanStack Virtual** (`@tanstack/svelte-virtual` 3.13, MIT, about 10 KB gzipped with its core; works with Svelte 5 through a store): built around items it can measure, while a row of a responsive grid is a run of tiles the layout decides, so the rows, measuring and blocks would still be mine, and one window per group fights its idea of where the list starts. **virtua** (0.54, MIT, about 8 KB gzipped; Svelte 5 components): its components draw their own containers and place items themselves, which a CSS grid, a shelf of spines and a table can't live inside without changing the look |
| Background changes on big pages | **Once a frame** (`store.itemsByFrame`, `core/store.svelte.ts`): the tiles and the pages that work a lot out from your whole library (the overview, Stats, a course, Curricula, Insights and the pages beside it, Connections, Rank) take changes to your entries at most once a frame; a redraw that's asked for (`render()`) is still immediate. The shell (top bar, sidebar, search box) takes none of them: it draws when it's asked to, as its HTML did (`core/shell/shell-state.svelte.ts`) | Measured: 300 covers arriving one at a time made the Svelte overview work every block out 300 times (43 s on the stress library, against 0.36 s for the HTML page); once a frame, 0.37 s. Insights, which still took every change, took 16 to 21 s for the same burst (`tests/stress/shell.ts`). Nothing visible changes: a frame is the soonest anything can be seen | Throttling with a timer (a delay you can see, and still several passes per burst); per-entry stores for each tile (every block reads many entries, so it wouldn't stop the blocks working everything out again); the shell reading the store like a page (it would recount every mode and list once a frame through a burst, for counts its HTML only updated when asked) |
| The overview's masonry | **My own packing**, kept from the HTML page (`packBlocks`, `fitRows` in `library/blocks.ts`, run by `BlockGrid.svelte` when what's in it, its width or a picture changes): each block spans as many 6px rows as it's tall, and dense packing fills the gaps; rows of covers end on a whole row | Twenty lines, and the blocks stay ordinary grid items, so widths (S/M/L/Full), arranging and the styles are unchanged | CSS `grid-template-rows: masonry` (not in Chrome yet); **Masonry**/**Colcade** (MIT): absolutely positioned columns, which would change the order blocks read in and how widths span |
| Dragging on the library page | **The browser's drag and drop**, my own code (`library/page/LibraryPage.svelte`, `dnd.ts`): covers dropped beside another (your shelf or ranking order), onto another and held (combine), onto a group's plaque (status or type); several selected at once; and the box you drag over covers to select them | Small and specific: what the library needs (several at once, hold to combine, a plaque as a target, your order kept among equal scores) are the parts libraries don't do. Every change it makes is an ordinary save, so it can be undone. Without a mouse, the bar for what you've selected makes the same status, type, combine and list changes; putting covers in an order of your own still needs one | **svelte-dnd-action** (0.9.80, MIT, about 14 KB gzipped, Svelte 5): keyboard and touch dragging, but by moving items within a list it owns; it has no combining, no dropping on a heading, needs every item drawn (it can't work with long lists drawn in part), and its moving animation would change the look |
| Dragging on tier lists | **The browser's drag and drop**, my own code, kept as it was and moved into the page (`library/tiers/TierListPage.svelte`): one entry or everything selected, dropped on a tier, before another entry, into the ranked column or back to the unplaced; the box you drag around several; keys (1–9, 0, Delete, Esc, Ctrl/⌘A, Q, /) and quick rank | About 150 lines for exactly what a tier list does, with the marks it shows (what's dragged, what it's over, what the box covers) as the page's own state now, so Svelte never sets back a class set from outside. Without a mouse, selecting and the number keys do everything dragging does | **svelte-dnd-action** (rejected for the library page, above: it moves items within lists it owns, has no box selection or several at once, and its animation changes the look); **SortableJS** (MIT, about 15 KB gzipped): sorts within and between lists, but draws its own ghost and fallback, and has no box selection, keys or several at once without its plugins, which would change the look and the browser tests' selectors |
| Dragging rows and tiles into place | **The browser's drag and drop, my own code**: one small class (`library/lists/reorder.svelte.ts`, about 60 lines) that a page hands its drag events to, for a list's rows, Up next and the overview's Next up, favourites and characters; the tabs bar has its own few lines (`core/shell/TabsBar.svelte`, shared with the tab editor) | It replaces the shared listeners in `core/events.ts` that set classes on elements Svelte now draws (Svelte would set them back): the marks are the page's own state, and each page's dragging goes when the page does. Dropping one on another still puts it before or after that one, saved as before, so undo works. Without a mouse, ↑ ↓ on a list's rows and the right-click menus move things too | **svelte-dnd-action** (rejected for the library page, above: it moves items within lists it owns, and its animation changes the look); **SortableJS** (MIT, about 15 KB gzipped): its own ghost and fallback, and favourites and characters are CSS grids it would want to reflow as you drag |
| The search box | **My own** (`core/shell/Search.svelte`, `searchView` in `core/search.ts`): one box, results in a column per kind of thing with the web's arriving per column, ↑ ↓ through every row, Enter, Escape, ＋ to add at once | Kept tag for tag, so the look and the browser tests' selectors are unchanged; the keyboard runs through rows in five columns, the characters, the lists and "Add it yourself", which a listbox component would lay out as one list | **Bits UI** Combobox (MIT, Svelte 5) and **Melt UI**'s combobox: their own listbox markup, ARIA and positioning, one list of options, and a filtered input they own (the box here searches the web as you type); **cmdk-sv**: a command menu with its own markup and styles |
| Fonts | **Fontsource**, bundled: the built-in themes' fonts, woff2 only, registered in `look/fonts.ts`, downloaded the first time a theme uses them and then kept for offline use (the service worker's `on-first-use` cache) | They work offline and no visitor's browser asks Google for them. A font someone picks from the longer list comes from Google Fonts, and the privacy page says so | Google Fonts for everything: no build size, but every visitor's address goes to Google |
| Your library | **IndexedDB**, in the browser | The only browser storage that holds this much; survives restarts, works offline, and the app asks the browser to keep it (`navigator.storage.persist`) | SQLite in WebAssembly: real SQL, about 1 MB more to download, for queries this app doesn't need |
| Backups | **The export zip** (format 3, [data-format.md](data-format.md)), written and read in the browser by a small zip reader and writer of my own (`import-export/importers.ts`): stored, not compressed, since pictures already are; reading is capped against zip bombs, and refuses with a reason what it can't open (a password, compression other than deflate, a damaged entry) | Works offline both ways, and needs no library for a few hundred lines. fflate is never shipped: it's only used while building and testing (the tests build zips with it, the identity guard `tools/guard.ts` looks inside zips with it, and `tools/pack-extensions.ts` packs the extensions) | JSZip, fflate in the app: more code shipped for compression the pictures don't need |
| Opening comics and books | **The same zip reader of my own** (`unzip` in `import-export/importers.ts`), for CBZ and EPUB files in the reader too: it inflates with the browser's own `DecompressionStream`, and stops an entry past its cap (`ZIP_LIMITS`: 512 MB an entry, 2 GB in all) as it streams | Weighed again when the reader moved to Svelte, on the same files in the same browser: a 300-page CBZ (42 MB, stored) opened in 13 ms against fflate's 17 ms; 400 deflated EPUB chapters (40 MB) in 105 ms against 51 ms, but fflate's `unzipSync` holds the page while it runs and its async form needs a worker of its own; and a 300 MB entry of zeros (a zip bomb in miniature) is stopped by the cap as it streams, while `unzipSync` inflates all of it into memory first (768 ms, no cap). fflate would add about 22 KB gzipped to every page for a reader most people never open | fflate (`unzipSync`, `unzip`); JSZip (larger, slower) |
| The player and the reader | **Svelte for everything around them, the video and the pages written by small attached code** (`watch-read/player/video.ts`, `pcPart` in `player.ts`, `rdTrack` in `read.ts`): the player is drawn once per video, its controls are written on the video's own events, a long strip keeps its images as you scroll | A video redrawn by the page starts again from the beginning; a control bar drawn through state would redraw four times a second while it plays. Measured on `tests/stress/reader-big.ts` and the player's browser test (`player-keeps-playing.ts`): nothing the page does around the video (settings, servers, the Watched tick, moving a button) loads it again | Everything through state (redraws on `timeupdate`); a video element kept outside Svelte and moved in by hand (two owners for one element) |
| Icons | **One component** (`core/Icon.svelte`) showing the app's own SVG strings (`ICON` in `core/shell.ts`) by a typed name | The icons are fixed markup written here; one place inserts them, and a name outside the table is a type error | An icon package (more to download for about twenty icons); an `{@html}` at each use |
| CSV import | **Papa Parse** 5.7.0 (MIT), about 19 KB (7 KB gzipped), fetched only when a CSV import starts (`import()` in `core/core.ts` `parseCSV`; the website keeps the file for offline use, the one-file build carries it inside) | Exports from other sites and spreadsheets are messier than the hand-written reader handled: semicolon and tab files from Excel set to other languages, quotes and line breaks inside cells, a column name used twice. It works out the separator itself and is the most used CSV reader there is | Keeping the hand-written reader (commas only, and a column whose name was used twice was lost) |
| Searching your library | **uFuzzy** 1.0.19 (MIT), about 8 KB (4 KB gzipped), part of the app (the search box is on every page) | Forgives a typo ("fullmetal alchmist") and works in every script (巨人 finds 進撃の巨人), fast enough on 10,000 titles to run on every key, with the titles folded once per change to the library | Fuse.js (larger, slower on long lists); keeping the plain "contains" match (no typos, and nothing beyond a–z) |
| Video | The browser's **`<video>`** | MP4 and WebM play natively. For other containers, the local media player's companion rewraps them as MP4 while they play (ffmpeg, on your own machine) | — |
| Build | **Vite** | Instant reload while working, and two outputs from one source: the website and the one-file build (`vite-plugin-singlefile`) | — |
| Offline and install | **vite-plugin-pwa** (Workbox) | After the first visit the site opens with no internet, and it can be installed | — |

## Accounts and the server

| Part | Chosen | Why | Weighed against |
| --- | --- | --- | --- |
| Hosting | **Cloudflare Workers with static assets** | Requests for the site's files are free and unlimited, `/api` runs in the same deploy at the same address, and the free plan allows any use | Netlify: separate functions and limits. Vercel: its free plan is non-commercial only and caps bandwidth |
| Server code | **One Worker** (`worker/`), strict TypeScript, with the few Cloudflare types it uses declared in `worker/env.d.ts` | Small: it hides catalogue keys that must stay secret, and runs Account & sync. The proxy people copy from Settings › Data is `worker/proxy.ts` turned into plain JavaScript as the app is built (`vite.config.ts`), so the copy can't drift from what the site runs | `@cloudflare/workers-types` (a whole package for a dozen types) |
| Sign-in | **Passkeys**, checked with **SimpleWebAuthn**, plus a recovery code | No passwords to leak, guess or reset. SimpleWebAuthn is reviewed and widely used, so there's no home-made WebAuthn parsing | Email and password; magic links (both need an email address, which the app never asks for) |
| Sync storage | **D1** (accounts, sessions) and **R2** (the encrypted library) | Both free at this size, and the Worker caps use so they stay free whatever anyone does ([hosting.md](hosting.md)) | — |
| Encryption | The browser's **WebCrypto** (AES-256-GCM, passkey PRF) | Built into every browser, nothing to download, nothing home-made | libsodium in WebAssembly |
| QR codes | **uqr** | Tiny, no dependencies, draws an SVG | qrcode (larger) |
| Catalogue keys | **The site lends its own TMDB and IGDB keys** through `/api`, cached for a day and limited per address | Films, TV and games then work for every visitor with nothing to sign up for. Only those two: RAWG's free plan is 20,000 lookups a month and personal, Comic Vine's terms are strict, and ScreenScraper and Hardcover keys belong to one person's account | Asking every visitor for keys (nobody does it) |
| Bot protection | **None beyond passkeys and limits** | Signing up needs a passkey, accounts are capped, and empty ones are cleared after a week. A CAPTCHA would add a third-party script to every page | Cloudflare Turnstile |

## Tools

| Part | Chosen | Why | Weighed against |
| --- | --- | --- | --- |
| Packages | **pnpm** | Fast, strict about what each package may use, one lockfile | npm |
| Format and lint | **Biome** (pinned), `biome check` in `pnpm lint`: the lint rules and the layout, so a file that isn't formatted fails the check | One tool and one config for both | ESLint plus Prettier |
| Unused code | **Knip** (pinned) | Finds unused files, exports and packages | — |
| Types | **svelte-check** for the app; **tsc** for the tests and tools (`tests/tsconfig.json`: they hold no components) and for the Worker; **@types/node** (pinned to the version the toolchain already brought in) for the tests and tools | svelte-check checks TypeScript and Svelte components together; the tests' callbacks run in the page, so their project has both the DOM's types and Node's, and the app's own types through the test hook | — |
| Import paths | **No extension** on imports of modules (`./core`, `../library/library`); `.svelte` files keep theirs (`./store.svelte` is `store.svelte.ts`), and what Node runs directly (the browser and stress tests, `tools/`) names the `.ts` file it imports (`./env.ts`), since Node finds files by their real name (`allowImportingTsExtensions` in `tests/tsconfig.json`) | It let each module turn from JavaScript into TypeScript without changing a line that imports it, and keeps imports the same if a module's file changes again. Vite, Vitest and TypeScript (`moduleResolution: "bundler"`) all find the file | `.js` on every import (what Node wants, but it names a file that doesn't exist); `.ts` with `allowImportingTsExtensions` |
| Unit tests | **Vitest** | Shares Vite's setup; runs in milliseconds | Jest |
| Running the TypeScript tests and tools | **Node's own type stripping**: `node tests/e2e/run.ts`, `node tools/guard.ts`, on by default from Node 22.18 (`engines` in `package.json`) and in Node 26, which CI uses. So they use only TypeScript that erases (no enums, namespaces or parameter properties), and `svelte.config.ts` is loaded the same way by Vite's Svelte plugin and svelte-check | Nothing to install or build first, and the file that runs is the file you read. The identity guard runs in CI before anything else is trusted, and on your own machine, with no build step in between | **tsx** (a dependency, and a loader between Node and the file); compiling the tests to JavaScript first (a second copy to keep in step); keeping them `.cjs` (untyped, so a test could call a name the app no longer has) |
| Browser tests | **Playwright** | Whole flows in a real browser, including passkeys (a virtual authenticator) and the site under its real headers | Cypress |
| The browser tests' way in | **A test hook in test builds only**: `window.__ulTest` (`core/test-hook.ts`), the names the browser tests and extensions' suites call inside `page.evaluate` (`__ulTest.items`, `__ulTest.goSettings`), each read live from its module and typed for the tests (`tests/hook.d.ts`). `start.ts` installs it only when `__UL_TEST_HOOK__` is true, a constant Vite writes in (`vite.config.ts`): true only in the modes `e2e` and `file-e2e` (`pnpm build:e2e` → `dist-e2e/`, `dist-file-e2e/`), so every other build drops the call and the module. `pnpm build` and `pnpm build:file` check what they built for it and fail if it's there (`tools/no-test-hook.ts`; a unit test checks the check) | Nothing of the tests ships (it replaced a bridge that put over 700 of the app's names on `window` for every visitor). The tests stay as close to what ships as they can: the same source, the same Vite settings and plugins, one constant apart. Built with the hook off, the test modes give byte-for-byte the files `pnpm build` and `pnpm build:file` give, so the only difference the tests see is the hook itself. The trade-off: the browser tests run against a build that has the hook, not the very bytes that deploy; what deploys is checked for the hook, and built in CI from the same commit | Keeping the bridge in production (the app's insides on `window` for every visitor); testing the production files through the page alone (every test rewritten to click its way to a state it now sets in one line); a separate entry file for tests (a different module graph, so a different bundle); checking `import.meta.env.MODE` in the app (Vite folds it the same way, but the app would then name the test modes; one named switch says what it's for) |
| Dialogs and menus | **My own overlay** (`core/modals.ts`): `role="dialog"`, `aria-modal`, the page behind made `inert` while one is open (so Tab stays inside), focus moved in and given back, Escape to close; and **my own menu box** (`#ctx`, `core/keys.ts`): placed inside the window, closed by a click elsewhere, Escape or a scroll away. Every dialog and menu is drawn by Svelte (`core/dialogs.ts`, `core/menus.ts`: every dialog, every right-click menu, and the small menus a button opens), mounted inside the same frame and box, so they get all of this unchanged | Every dialog is Svelte now, each the old markup tag for tag, checked pixel by pixel: a component library draws its own markup and styles (and its own focus trap and positioning), which would change the look and the browser tests' selectors at once, for behaviour the overlay already has and the tests already check (focus, Escape, `inert`; axe checks the markup). With the last string dialogs moved (Adjust a picture, a show's servers), the overlay's own code is what's left: about 90 lines of opening, closing, `inert` and focus that the browser tests check, so it stays | Bits UI 2 (MIT, Svelte 5; headless, but its Dialog renders its own portal, overlay and focus scope), Melt UI (MIT; builders with the same focus and portal handling), Floating UI for placing the menu (MIT; about 3 KB for what eight lines of clamping do) |
| Moving screens to Svelte | **One screen at a time, markup unchanged** ([architecture.md](architecture.md#moving-a-screen-to-svelte)): the same tags, classes, ids and `data-act` names; state through the store; fields and the component's own buttons handled in the component, buttons that change the library left to the `handlers.ts` files; pieces many screens draw (the tiles) a component as soon as one moved screen needs them, with the older screens' string drawn from the same code; no library added. Checked by before and after screenshots compared pixel by pixel | Each screen can be checked against the browser tests that already cover it, and nothing a person sees changes. Drawing a dialog once and updating it in place is what fixes the bugs the rewrites are for: the item card lost what you'd typed when you pressed another button on it, and its Edit details couldn't change an entry's medium; Edit profile wiped what you were typing when you picked a banner, and a reading's Edit section closed after every change; a franchise's card went to the mode's first tab instead of opening, the sidebar's Customise menu stayed open after a click elsewhere, the mode button still said its menu was open after Escape closed it, a list's name box stayed empty after you emptied it, and two controls had no name for a screen reader (the overview's Next up covers, a list's Sort menu) | Rewriting all the screens at once; changing the markup and styles as each moves (the look would drift, and every browser test selector would break at once) |
| Charts | **My own, as Svelte components drawing HTML, CSS and a little SVG** (`library/blocks/`: `Bars` for every bar chart in the app, finishing rates included; `Chart` for bars, columns, a donut or a list; `GapChart`; `Heat`; `library/stats/StackChart` for the stacked columns), worked out in `blocks/charts.ts` | Insights, the overview and Stats show horizontal bars, columns, a donut, an activity grid and stacked columns. They're themed by the same custom properties as everything else and laid out by the page's own grid, and moving them to components kept them pixel for pixel as they were (one component for the bars everywhere, where there had been two strings embedded in several pages) | **LayerChart** (MIT, Svelte 5, on D3 scales) and **Chart.js** (MIT, canvas): both draw their own axes, labels, spacing and tooltips (a canvas can't take the theme's fonts and colours from CSS as it changes), so the charts couldn't look the same, for about 40 to 70 KB gzipped more; worth another look if a page ever needs real charts (lines over time, scatter with zoom) |
| Accessibility | **axe-core**, in the browser tests | Checks every page and the main dialogs against WCAG 2.1 AA on every change. Used only in tests (MPL-2.0), never shipped | Lighthouse (one page at a time) |
| Deploys | **GitHub Actions** | The steps live in the repo: check, test, build, and deploy only if all of it passes | Cloudflare's own Git builds |
